# 실행과 운영

## 기본 실행

프로젝트 루트에서 실행한다. Docker Engine과 Compose가 필요하다. Mac에서는 Docker Desktop 등 Linux 컨테이너 실행 환경을 사용한다.

```sh
test -e .env || cp .env.example .env
mkdir -p incoming managed
docker compose up -d --build
```

브라우저에서 `http://127.0.0.1:8888`을 연다. 기존 `.env`는 위 명령으로 덮어쓰지 않는다. 이 명령의 디렉터리 생성은 기본값 기준이며, 라이브러리 위치를 바꿨으면 설정한 경로에 두 디렉터리를 먼저 생성한다.

`incoming`에 사진·영상을 넣고 화면의 **새로 고침**을 눌러 검사를 시작한다. 앱 시작이나 폴더 변경만으로 검사를 자동 실행하지 않는다. 전체 사용 흐름은 [사용자 가이드](user-guide.md)에 정리했다.

## 환경 변수

사용자 설정 예시는 [.env.example](../.env.example), 마운트와 서비스 연결은 [compose.yaml](../compose.yaml)을 따른다.

| 변수 | 기본값 | 용도 |
| --- | --- | --- |
| `PHOTO_SAVER_PORT` | `8888` | 호스트의 웹 포트. `127.0.0.1`에 바인딩 |
| `PHOTO_SAVER_TIMEZONE` | `Asia/Seoul` | 기본 표시·해석 시간대. IANA 시간대 이름 사용 |
| `PHOTO_LIBRARY_ROOT` | `.` | 호스트 라이브러리 루트. 상대 경로는 Compose 프로젝트 기준 |
| `INCOMING_DIR` | `incoming` | 라이브러리 루트 아래 수집 디렉터리의 상대 경로 |
| `MANAGED_DIR` | `managed` | 라이브러리 루트 아래 보관 디렉터리의 상대 경로 |
| `PHOTO_SAVER_STORAGE_USER` | 빈 값 | SSH 접속 계정. API와 워커에 전달 |

스토리지 IP와 원격 저장 절대경로는 `.env`가 아니라 웹의 **설정** 페이지에서 저장한다. SSH 계정은 `.env`에 지정한다. 설정 화면에는 계정과 공개키를 마스킹해서 표시한다.

코드에는 내부 실행 경로를 위한 변수도 있다. `PHOTO_SAVER_DATA`의 기본값은 `/data`, `PHOTO_SAVER_THUMBNAILS`는 `/thumbnails`, `PHOTO_SAVER_LIBRARY`는 `/library`다. 현재 Compose는 이 세 변수를 호스트 `.env`에서 서비스로 전달하지 않는다. 변경하려면 Compose 환경 설정과 볼륨 대상도 함께 조정해야 한다. SSH 설정 디렉터리 `/settings`는 코드에 고정되어 있다.

## 라이브러리 경로 조건

워커 시작 시 다음을 검사한다.

- `INCOMING_DIR`, `MANAGED_DIR`는 라이브러리 아래의 상대 경로여야 한다.
- 두 경로가 서로 같거나 부모·자식 관계이면 안 된다.
- 경로 구성 요소가 심볼릭 링크가 아니어야 하며 디렉터리가 미리 존재해야 한다.
- 워커에 읽기·쓰기·탐색 권한이 있어야 한다.
- 두 디렉터리는 같은 파일시스템이어야 한다. 원본 이동은 덮어쓰지 않는 `renameat2`를 사용한다.

Compose의 bind mount는 `create_host_path: false`로 설정되어 있다. 경로가 없으면 자동으로 디렉터리를 만들지 않는다. API는 원본 미리보기용 Incoming만 `/incoming-preview`에 읽기 전용으로 마운트한다. 워커에는 라이브러리 루트가 `/library`로 마운트되므로 기본값처럼 라이브러리 루트를 프로젝트로 두면 워커가 프로젝트 전체에 접근할 수 있다.

복사가 끝나기 전에 검사하지 않도록 임시 확장자로 복사한 후 최종 이름으로 바꾸거나, 별도 위치에서 복사를 마친 뒤 Incoming으로 옮긴다.

## 서비스 확인과 변경 반영

```sh
docker compose config --quiet
docker compose ps
curl --fail http://127.0.0.1:8888/api/health
docker compose logs --tail=100 api worker frontend
```

헬스 응답은 `{"status":"ok"}`다. API의 컨테이너 헬스 체크는 3초 주기이며 frontend와 worker는 API가 healthy가 된 후 시작한다. 헬스 응답은 워커나 원격 스토리지 연결 상태까지 확인하지 않는다.

설정 변경 후에는 다음과 같이 컨테이너를 재생성한다. `.env` 변경을 반영할 때 `restart`만으로는 충분하지 않다.

```sh
docker compose up -d
```

백엔드 Python 코드·의존성·Dockerfile 변경 후에는 이미지를 다시 빌드한다.

```sh
docker compose up -d --build
```

프론트엔드는 호스트 파일을 읽기 전용 마운트하므로 소스 수정 후 브라우저를 새로 고침한다. 백엔드 소스는 이미지에 복사되며 개발용 자동 재시작 설정은 없다. frontend에는 별도 `restart` 정책이 없고 api·worker에는 `unless-stopped`가 적용된다.

## 영속 데이터와 백업

| 위치 | 보관 내용 |
| --- | --- |
| 호스트 `incoming` | 아직 이동하지 않은 원본과 부가 파일 |
| 호스트 `managed` | 이동된 원본과 연결한 XMP |
| `catalog` 명명 볼륨 | `/data/catalog.sqlite3`, WAL 관련 파일, 잠금 파일 |
| `thumbnails` 명명 볼륨 | 해시 기반 JPEG 썸네일 |
| `settings` 명명 볼륨 | 원격 주소·루트, SSH 개인키·공개키, 공개키 복사 표시, 호스트 키 |

기본 종료는 다음과 같다.

```sh
docker compose down
```

일반 `down`은 명명 볼륨을 유지한다. `down -v`는 카탈로그·SSH 설정·썸네일 볼륨을 제거하므로 데이터 보존이 필요할 때 사용하지 않는다. 호스트 원본과 원격 아카이브는 별도 보관 대상이다.

카탈로그는 **설정 → 카탈로그 백업**으로 내려받는다. 백업·복원은 활성 작업이 없을 때 가능하다. 이 파일은 SQLite 데이터만 포함하며 원본·썸네일·SSH 키·접속 설정을 포함하지 않는다. 복원은 현재 카탈로그 내용을 교체하고, 복원된 대기·실행 작업은 재실행하지 않고 실패로 바꾼다. 세부 동작은 [아카이브와 스토리지](archive-and-storage.md)를 참고한다.

## 문제 해결

| 증상 | 확인할 내용 |
| --- | --- |
| 컨테이너 생성 시 경로 오류 | 설정한 라이브러리와 Incoming 디렉터리 존재 여부, Docker 파일 공유 접근 |
| 워커가 시작하지 않음 | 두 디렉터리의 권한·상대 경로·중첩·같은 파일시스템 조건, `worker` 로그 |
| API는 정상이지만 검사가 계속 대기 | `worker` 실행 상태와 로그. 헬스 체크는 API만 검사 |
| 파일이 보이지 않음 | 지원 확장자, 수동 검사 여부, 심볼릭 링크 여부. 복사 중이거나 변경된 파일은 확인 필요 상태 가능 |
| 미리보기에서 파일 변경 오류 | 검사 후 원본이 변경·이동되었는지 확인하고 Incoming 새로 고침 |
| 작업 등록에서 409 | 검사·이동·삭제·XMP 연결·업로드 전체 중 다른 활성 작업이 있는지 확인 |
| SSH 인증 실패 | `.env` 계정 반영 여부, 공개키 등록, SSH 서비스의 22번 포트, 서버 호스트 키 승인 |
| 서버 호스트 키 불일치 | 서버의 실제 키와 저장된 키를 운영자가 확인. 현재 UI에는 기존 호스트 키 교체 기능이 없음 |
| 원격 폴더를 조회할 수 없음 | IP·절대경로·읽기 권한·SFTP 지원·연결 상태 |
| 일부 파일 업로드 실패 | 대상 동명 파일의 해시 충돌, 로컬 원본 변경, 원격 쓰기 권한과 디스크 공간, 실패 목록 |
| 백업·복원에서 409/413 | 진행 작업 종료 여부, 복원 파일 128MiB 제한 |

현재 네트워크 장애 후 자동 대기·백오프 재시도는 없다. 완료한 파일은 유지되므로 연결을 복구한 뒤 필요한 항목을 다시 선택해 업로드한다. 로그인·권한 관리가 없는 로컬 단일 사용자 구성으로, 웹 포트는 기본적으로 루프백에만 공개한다.
