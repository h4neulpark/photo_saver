# 수집과 미디어 처리

## 기기 업로드에서 검사까지

Incoming의 **기기에서 업로드**는 사진 → 영상 → XMP·THM·LRV 순으로 전송한다. 미지원 형식과 0바이트 파일은 제외 결과를 남기며 다른 파일은 계속 처리한다. 기본 파일 한도는 100GiB, 청크는 8MiB(상한 32MiB)이고 .photo-saver-uploads/ staging에만 기록한다. scan_tree는 숨김 폴더를 제외하므로 미완료 파일을 분석하지 않는다.

서버는 완료 시 크기 검증과 fsync 후 원자적으로 게시한다. 이름 충돌은 기존 원본을 보존하고 (1)부터 (9999)까지 번호를 붙인다. 유효한 last_modified_ms는 파일 수정시각에 보존하고 확장자만 검증하므로 실제 미디어 유효성·메타데이터 분석은 이후 기존 파일 검사에서 수행한다.

같은 배치의 원본이 개명되면 정확한 파일명과 비모호 stem 매핑으로 IMG_0001.xmp 및 IMG_0001.HEIC.xmp를 각각 IMG_0001 (1).xmp, IMG_0001 (1).HEIC.xmp로 조정한다. 폴더별로 격리하며 동일 stem의 복수 원본이 있으면 stem 매핑을 적용하지 않는다. 기존 동반 파일 연결 규칙은 이후 검사에서 그대로 적용된다.

이 문서는 현재 구현된 로컬 파일 처리 흐름을 정리한다. 관련 코드는 [worker.py](../backend/worker.py), [media.py](../backend/media.py), [companions.py](../backend/companions.py), [api.py](../backend/api.py)다.

## 처리 범위와 파일 배치

| 구분 | 지원 대상 |
| --- | --- |
| 사진 | `.jpg`, `.jpeg`, `.png`, `.webp`, `.heic`, `.heif` |
| 영상 | `.mp4`, `.mov` |
| 동반 파일 | `.xmp`, `.thm`, `.lrv` |

확장자는 대소문자를 구분하지 않는다. 스캔은 하위 디렉터리를 순회하며 숨김 파일·디렉터리, 심볼릭 링크 파일, 지원하지 않는 확장자를 제외한다. 임시 확장자로 복사한 뒤 최종 이름으로 변경하면 완성되지 않은 파일의 검사를 줄일 수 있다.

```text
라이브러리 루트 (/library)
├── incoming/                         # 사용자가 수집한 원본
└── managed/
    └── <원본 파일 ID>/
        ├── IMG_0001.HEIC             # 승인 후 이동한 원본
        └── IMG_0001.xmp              # 연결된 XMP

썸네일 볼륨 (/thumbnails)
└── <SHA-256>-v1.jpg
```

`INCOMING_DIR`과 `MANAGED_DIR`은 라이브러리 아래의 상대 경로이며, 서로 겹치지 않아야 한다. 워커는 두 디렉터리가 존재하고 읽기·쓰기·탐색 권한이 있으며 같은 파일시스템에 있는지 시작 시 확인한다. 경로 구성 요소에 심볼릭 링크를 허용하지 않는다. 이미 `managed`에 있던 지원 파일도 수동 스캔에서 분석하며, 이 파일은 기존 상대 경로를 유지한다.

## 수동 검사와 중복 판정

1. **Incoming Library → 파일 검사**는 `scan` 작업을 등록한다. 화면은 보관 파일 확인, Incoming 해시 계산, 썸네일 생성, 동반 파일 확인의 진행 단계를 표시한다.
2. 워커는 `managed`를 먼저 색인한다. 기존 파일의 상태 지문이 같으면 저장한 해시와 분석 결과를 재사용한다. 변경되었거나 새로 발견한 파일은 SHA-256과 메타데이터를 다시 계산한다. 사라졌거나 읽을 수 없는 기존 파일은 `missing`으로 표시한다.
3. `incoming`의 대상 목록을 수집하고, 대상이 있으면 0.4초 대기한 뒤 파일별 SHA-256을 계산한다. 목록 수집 당시 상태와 해시 계산 전후의 상태가 같아야 한다.
4. 유효한 `managed` 파일의 해시, `remote_files(status='present')`의 원격 아카이브 해시, 또는 이번 검사에서 먼저 발견한 파일의 해시와 비교한다. 이름이 달라도 바이트가 같으면 중복이다. 로컬 `managed`에서 비운 파일이라도 원격 아카이브에 보관 중이면 `원격 아카이브의 <경로>에 이미 보관됨` 사유와 함께 `duplicate`로 분류한다. 같은 검사 안에서만 중복이면 첫 파일을 이동 후보로 남긴다.
5. 이동 승인 전에도 썸네일을 생성한다. 해시가 같은 파일은 캐시를 공유한다. 새 검사를 완료하는 트랜잭션에서 검사 결과와 XMP 후보를 저장하고, 이전 스캔의 `scan_files`·`scan_xmp` 행은 모두 제거한다. 삭제·이동 결과를 포함한 Incoming 파일별 기록은 다음 검사까지 남으며, 과거 작업의 `jobs` 기록은 유지된다.

파일 상태 지문은 장치 ID, inode, 크기, 수정 시각(ns), 변경 시각(ns)의 JSON 배열이다. 파일을 열 때와 작업 전후에 지문을 비교하고 일반 파일인지 확인한다. 읽는 동안 바뀐 파일은 검토 대상으로 돌린다.

| `scan_files.status` | 의미 |
| --- | --- |
| `ready` | `managed`의 유효한 동일 사본이 없는 이동 후보 |
| `duplicate` | `managed` 또는 이번 검사의 다른 후보와 같은 콘텐츠 |
| `review` | 파일 변경, 읽기 실패, 이동·삭제 실패 등으로 재확인 필요 |
| `moved` | 이동과 카탈로그 등록 완료 |
| `deleting` | 사진 삭제 의도를 기록하고 처리 중 |
| `deleted` | 사진 삭제 또는 중복 정리 완료 |

**확인 필요** 파일은 표시된 사유에 따라 원본·접근 권한·원격 사본을 점검한 뒤 다시 검사한다. 이동·삭제된 항목의 경로와 파일별 결과는 처리 작업에 남으며 일반 Incoming 목록에서는 제외된다.

## 승인된 원본 이동과 복구

**선택 항목을 managed로 이동**은 최신 검사의 `ready` 항목만 받는다. 워커는 원본 지문과 유효한 `managed` 중복을 이동 직전에 다시 확인한다. 이후에 발견한 중복은 `duplicate`로 바꾸고 `incoming`에 남긴다.

이동 전에 `media`에 목표 경로와 `moving` 상태를 기록한다. 실제 파일 이동은 Linux `renameat2(RENAME_NOREPLACE)`로 처리하여 같은 파일시스템 안에서 이름을 바꾸고 대상 파일을 덮어쓰지 않는다. 이동 후 신원이 예상과 다르면 해시를 다시 검증한다. 분석 결과를 저장한 뒤 `media.status=available`, 검사 결과는 `moved`가 된다. 이벤트 분류는 원본 파일을 다시 이동시키지 않는다.

워커 재시작 시 `running` 작업을 `queued`로 되돌린다. 이동 재실행에서는 다음을 확인한다.

- `moving` 기록의 대상 파일이 있으면 SHA-256을 검사하여 이어서 분석한다. 다른 콘텐츠가 있으면 `review`다.
- 대상이 없으면 원본 지문과 중복을 다시 확인하고 이동을 재시도한다.
- 이미 `available`이면 원본 이동은 반복하지 않고 동반 파일 처리를 이어 간다.

파일별 `OSError`는 `review`로 기록하고 다음 항목을 처리한다. 작업 자체의 예상하지 못한 예외는 `failed`로 남는다.

## 사진 삭제

삭제는 최신 검사에서 `ready` 또는 `duplicate`인 **incoming 사진**만 가능하다. UI에서 대상 목록을 확인한 후 `delete` 작업을 등록한다. 워커는 지문과 SHA-256을 다시 검증하고 `deleting`을 기록한 뒤 파일을 영구 삭제한다. 영상, `managed` 원본과 원격 아카이브는 이 작업의 대상이 아니다.

재시작 후 `deleting` 파일이 이미 사라졌다면 삭제 완료로 복구한다. 처음 삭제를 시작할 때 사라졌거나 검사 후 변경된 파일은 `review`다. 삭제 후 같은 해시의 Incoming 항목을 다시 분류하여 남은 파일 중 하나가 이동 후보가 될 수 있도록 한다. `available`과 `archived` 어느 쪽에서도 참조하지 않게 된 해당 해시의 썸네일만 정리한다. 사진에 연결된 XMP·THM·LRV를 함께 삭제하는 동작은 없다.

## 확인된 중복 정리

`duplicate-cleanup`은 최근 검사에서 중복인 사진과 영상에 적용한다. 앱은 해시 그룹마다 사용자가 지정한 남길 사본과 정리할 Incoming 파일을 예약한다. 같은 Incoming 검사의 사본을 선택하면 그 사본은 정리 대상에서 제외한다. managed 사본은 활성 offload 목록에서 제외된 파일을 고르고, 정리가 진행되는 동안 해당 사본의 offload 등록을 차단한다.

워커는 정리 대상의 지문과 SHA-256을 대조한다. 남길 로컬 사본은 파일 지문과 SHA-256을, 원격 사본은 현재 스토리지와 루트의 검증 기록 및 실시간 SFTP 파일의 SHA-256을 확인한다. 원격 해시는 업로드와 같은 SSH 우선·SFTP 대체 경로로 검사한다. 실제 삭제 직전에 남길 사본의 상태를 다시 확인한다. 불일치 또는 연결·읽기 실패 시 Incoming 파일을 보존하고 파일별 확인 사유를 기록한다. XMP·THM·LRV는 별도 보존한다.

## 메타데이터, 썸네일과 미리보기

| 처리 | 현재 동작 |
| --- | --- |
| 사진 분석 | Pillow와 `pillow-heif`로 형식·크기, EXIF 제조사·모델·촬영 시각을 읽음 |
| 영상 분석 | `ffprobe`로 MOV/MP4 컨테이너와 스트림의 해상도·코덱·길이·장비·촬영 시각을 읽음 |
| 사진 썸네일 | EXIF 회전을 반영하고 최대 `360×240` JPEG 생성 |
| 영상 썸네일 | FFmpeg로 첫 영상 스트림의 대표 프레임 1장, 최대 `360×240`, 스레드 1개로 생성 |
| 캐시 | `<SHA-256>-v1.jpg`; Incoming에서 만든 캐시를 이동 후에도 재사용. Nginx `/thumbnails/`는 성공 응답(200·304)에 `Cache-Control: public, max-age=31536000, immutable`, 모든 응답에 `X-Content-Type-Options: nosniff`를 적용하며 404에는 장기 캐시를 부여하지 않음 |
| 분석 실패 | 오류를 메타데이터에 기록하고 파일 수정 시각을 참고값으로 사용. 썸네일은 없을 수 있음 |

Incoming 원본·미리보기 API는 최신 검사에 포함된 `ready`·`duplicate` 파일의 지문을 확인한다. 보관(`managed`) 파일도 `media.status=available`이고 지문이 유효하면 API의 `/managed-preview` 읽기 전용 마운트를 통해 `/api/managed/{file_id}/original`·`/preview`로 큰 사진 미리보기와 브라우저 영상 재생을 제공한다. 이때 파일 조회는 논리적 이벤트 폴더가 아니라 DB에 기록된 실제 물리 상대 경로(`managed/<파일 ID>/<원래 파일명>` 등)를 기준으로 하므로, 이벤트 배정·소분류 이동·확정 변경만으로 미리보기 경로나 파일 위치가 바뀌지 않는다.

공통 파이프라인에서 HEIC·HEIF 미리보기는 EXIF 회전을 반영한 최대 `2200×2200` JPEG로 변환해 전체 `200` 응답으로 제공하고, 다른 형식은 지문을 검증한 파일 디스크립터(`/proc/self/fd/<fd>`) 기반 `FileResponse`로 원본을 스트리밍한다. 영상 재생은 브라우저 코덱 지원에 따르며, `managed` 원본 응답은 단일 바이트 `Range`와 지문 기반 `ETag`/`If-Range`를 지원한다. 외부에서 변동된 파일은 지문 불일치(`409`)로 차단하고 새로 고침 재검사를 요구한다. 로컬 원본 비우기(`offload`)로 `archived` 상태가 된 파일은 로컬 원본이 없으므로 미리보기·원본 URL이 `null`이 되며 썸네일과 메타데이터만 유지된다.

### 촬영 시각

사진은 EXIF `DateTimeOriginal`, `DateTimeDigitized`, 일반 날짜 순으로 읽고 대응하는 UTC 오프셋 태그를 적용한다. 영상은 `com.apple.quicktime.creationdate`, `creation_time` 순으로 읽는다. 사진·영상·XMP의 메타데이터 해석은 공통 함수 `parse_capture_datetime()`을 사용하므로 모두 1980년 이전 값을 제외한다. 파일 수정 시각과 사용자가 직접 입력한 시각에는 이 연도 제한을 적용하지 않는다.

시간대가 명시되면 UTC로 정규화하고 `time_verified=1`을 기록한다. 시간대가 없으면 `PHOTO_SAVER_TIMEZONE`(기본 `Asia/Seoul`)을 가정하되 확인 대기로 둔다. 유효한 촬영 시각이 없으면 UTC 파일 수정 시각을 표시하고 확인 대기로 둔다. 사용자는 메타데이터, XMP, 수정 시각 또는 직접 입력을 선택해 확인할 수 있으며, 사용자 값은 원본 분석 결과와 별도로 보관한다.

XMP 시각만 있으면 그 값을 사용한다. 원본 현지 시각과 시간대가 있는 XMP 시각이 일치하면 XMP 오프셋으로 시간대를 보완한다. 두 근거가 충돌하면 **원본과 XMP 시각 불일치**로 표시하여 사용자가 출처를 선택하도록 한다.

### 장비와 GoPro·DJI

기본 장비명은 메타데이터 제조사·모델을 조합한다. 파일별 사용자 지정 장비가 있으면 우선하고, 그 다음 설정에 저장한 촬영도구 이름 규칙을 적용한다. 장비별 등록 규칙이나 파일명 기반 모델 추정은 구현되어 있지 않다.

GoPro는 컨테이너·스트림의 제조사, 인코더, 핸들러에 포함된 GoPro 표기 또는 `gpmd` 트랙으로 판별한다. 근거가 있을 때 ExifTool의 GoPro 전용 `Model`·`FirmwareVersion`을 추가 조회한다. 모델 조회 실패 시 제조사 GoPro만 남기며 파일명이나 펌웨어 문자열만으로 모델을 추측하지 않는다.

DJI는 ExifTool 추가 호출 없이 `ffprobe` 출력만으로 판별한다. 컨테이너·스트림의 `make`·`com.apple.quicktime.make`에 독립된 DJI 표기가 있거나, `encoder`·`handler_name`이 DJI와 구분자(공백·`.`·`_`·`/`·`-`)로 시작하거나 DJI 자체인 경우, 또는 `djmd`·`dbgi` 메타데이터 트랙이 있으면 제조사를 `DJI`로 기록한다. 태그의 제어 문자와 연속 공백은 정리하고, 감지 근거는 중복 없이 `device_evidence`에 저장한다. `encoder`의 DJI 접두사 뒤에 있는 원본 모델명은 대소문자·표기를 유지한다. 예를 들어 `DJI OsmoPocket3`는 제조사 `DJI`, 모델 `OsmoPocket3`, 기본 장비명 `DJI OsmoPocket3`가 된다. 일반 인코더·코덱·핸들러·버전 토큰만 있는 값은 모델로 쓰지 않으며, 제조사·핸들러·트랙 근거만 있으면 제조사만 남긴다. 컨테이너 인코더가 일반 값이어도 스트림 인코더에 모델이 있으면 보완한다. 파일명만으로 DJI나 모델을 추측하지 않는다.

명시된 타사 제조사·모델(예: `Apple`·`iPhone 16`)은 GoPro·DJI 판별과 ExifTool 조회를 건너뛰어 유지한다. GoPro가 먼저 확정되면 DJI로 덮어쓰지 않는다. DJI 제조사가 명시되어 있으면 빈 모델만 보완하고 기존 명시 모델은 보존한다. 자동 인식한 장비명은 설정의 **촬영도구 이름** 규칙에 그대로 연결되므로 `DJI OsmoPocket3`를 원하는 표시·폴더 이름으로 매핑할 수 있으며, 파일별 사용자 지정 이름이 우선한다.

영상 분석 버전은 현재 `3`이다. 로컬 원본이 있는 `available` 영상의 버전이 다르면 다음 스캔에서 한 번 재분석하며, 지문이 같은 파일은 해시를 다시 계산하지 않는다. 해시가 같은 원본은 사용자 장비·시각, 이벤트 배정·확정, XMP 연결 정보를 유지한다. 로컬 원본을 비운 `archived` 항목은 기존 메타데이터와 보관 상태를 유지한다.

## XMP와 카메라 보조 파일

동반 파일 연결은 기본적으로 같은 폴더와 대소문자를 무시한 파일명을 사용한다. `IMG_0001.HEIC.xmp`처럼 원본 확장자가 포함되면 해당 원본을 지정한다. `IMG_0001.xmp`에 사진과 영상 후보가 함께 있으면 유일한 사진을 우선하며, 후보가 모호하면 자동 연결하지 않는다.

XMP에서는 제목, 설명, 키워드, 도시·지역·국가·장소, GPS 문자열과 `photoshop:DateCreated` 또는 `exif:DateTimeOriginal`을 읽는다. XML은 `defusedxml`로 해석하고 분석 크기는 1 MiB까지다. 크기를 초과해도 해시는 계산하되 메타데이터에 오류를 남긴다.

- 신규 `ready` 원본의 XMP는 이동 시 `managed`의 원본 옆으로 옮긴다. 같은 대상 경로에 다른 콘텐츠가 있거나 다른 원본의 XMP이면 덮어쓰지 않는다.
- 중복 원본이나 먼저 이동한 원본의 XMP는 기존 해시·수집 경로·파일명으로 후보를 찾아 **XMP 연결** 목록에 표시한다. 사용자가 후보를 선택하면 `xmp-link` 작업이 다시 검증하고 이동한다. 상태는 `pending → linked` 또는 `review`다.
- `managed`에서 새로 발견한 XMP도 스캔 시 연결한다. 사라진 XMP의 연결 정보는 제거한다.
- `.THM`과 `.LRV`는 유일한 원본에만 연결한다. `.LRV`는 영상만 후보로 삼으며 GoPro `GL…`와 `GH…`/`GX…` 이름 대응도 지원한다. 원본의 이동·카탈로그 등록 후, 검사 당시 지문이 같은 보조 파일만 Incoming에서 삭제한다.
- 동반 파일 처리 실패는 원본 이동을 취소하지 않는다. 결과의 `companionReview`와 워커 로그에서 확인한다. 모호하거나 변경된 동반 파일은 남겨 둔다.

## 실행 제약

워커는 `worker.lock`으로 단일 프로세스를 보장한다. `WorkerCoordinator`는 기본 0.4초 폴링 및 스레드 완료 이벤트로 큐를 확인하고 한 DB 쓰기 트랜잭션에서 claim한다. `local` 스레드는 `scan`·`move`·`delete`·`duplicate-cleanup`·`xmp-link`를, `remote` 스레드는 `upload`·`offload`·`remote-index`를 실행해 최대 1+1 병렬로 처리한다. 같은 레인에는 활성 작업 하나만 허용한다. `exclusive` 작업(`reset-all`)이 대기·실행 중이면 다른 레인의 claim을 막고, 기존 스레드와 DB running 작업이 모두 끝난 뒤 코디네이터가 직접 실행한다. 기동 시 두 레인의 stale running을 queued로 복구하며 SIGTERM·SIGINT는 새 claim을 중단하고 실행 중인 스레드가 끝나기를 기다린다.

병렬 스캔은 missing/XMP 해제 갱신을 available에만 적용하고 분석 upsert는 offloading·archived를 덮어쓰지 않는다. 로컬 비우기는 삭제 직전 status·sha·path·xmp_path·xmp_sha를 한 SQL로 확인해 offloading으로 전환한다. 정보가 달라졌으면 삭제 없이 409로 거부한다. 활성 offload 대상의 XMP 연결은 API와 워커에서 거부하며, XMP 이동 후 원본 상태가 바뀌어 연결에 실패하면 옮긴 XMP를 Incoming으로 돌려놓는다. 삭제 후 썸네일 정리는 available·archived·offloading·moving 참조를 모두 보존한다.

UI는 로컬/원격 버튼을 각 레인의 활성 상태로 제한하고 exclusive 또는 백업·복원 요청 중에는 모두 잠근다. 전역 진행 배너에 두 레인을 함께 표시하고 원격 중지는 해당 작업 ID로 요청한다. 한 레인이 끝나도 다른 활성 레인이 있으면 폴링과 미리보기 삭제 추적을 계속한다.

`renameat2`와 `/proc/self/fd`를 사용하므로 파일 처리 구현은 Linux 컨테이너 실행을 기준으로 한다. 원본을 앱 외부에서 변경하면 다음 스캔에서 다시 검증하며, 처리 도중의 변경은 지문 검사로 감지한다.

## 전체 로컬 데이터 초기화

[resets.py](../backend/resets.py)의 `reset_local_data`는 managed·썸네일 디렉터리의 모든 항목과 카탈로그 볼륨의 임시 파일을 삭제한다. 숨김 파일·XMP·THM·LRV·이전 returned 폴더도 포함한다. 루트 디렉터리를 유지하고 하위 항목만 지운다. 링크는 링크 자체를 삭제하며 대상을 따라가지 않는다. 하위 마운트는 순회하지 않고 오류로 중단한다. 초기화 대상 루트가 겹치면 삭제 시작 전에 거부한다.

해시 계산이나 파일 이동 없이 삭제하고, 끝나면 카탈로그·작업 기록을 모두 비운다. SSH 설정·원격 아카이브는 유지한다. 실패 시 이미 지운 파일은 돌아오지 않는다. 중단 후 재시작 시 남아 있는 항목을 계속 삭제한다. incoming의 파일·하위 폴더는 초기화 대상에서 제외한다. 성공 후 수동 검사하면 보존한 incoming 파일을 다시 수집할 수 있다.
