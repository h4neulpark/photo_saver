# 아카이브 전송·스토리지 설정·파일 기록

이 문서는 현재 코드에 구현된 SSH/SFTP 연결, 원격 탐색, 전송 및 카탈로그 관리 동작을 설명한다. OMV 전용 API를 사용하지 않으므로 SSH와 SFTP를 지원하고 대상 계정이 저장 경로를 읽고 쓸 수 있는 스토리지에 연결할 수 있다.

## 1. 연결 설정

1. `.env`의 `PHOTO_SAVER_STORAGE_USER`에 원격 SSH 계정명을 설정하고 API와 워커에 반영한다.
2. **설정**에서 스토리지 IP와 원격 저장 절대경로를 등록한다. IP는 IPv4 또는 IPv6만 허용하며 호스트명, 포트 지정, scope가 있는 IPv6 주소는 지원하지 않는다. SSH 포트는 기본값인 22번을 사용한다.
3. **공개키 생성**으로 비밀번호가 없는 Ed25519 키 쌍을 만든다. 공개키를 복사해 원격 계정의 SSH 인증 키로 등록한다. 복사 완료를 기록한 뒤에는 앱에서 같은 공개키를 다시 조회할 수 없다. **공개키 재생성**은 기존 키 쌍을 교체하므로 새 공개키를 원격 계정에 다시 등록해야 한다.
4. **접속 테스트**에서 처음 접속하는 IP의 호스트 키 지문을 확인한다. 서버에서 확인한 지문과 비교한 뒤 승인하면 호스트 키를 저장하고 공개키 인증을 테스트한다. 승인 요청은 5분 후 만료된다.
5. **아카이브 전송 → 아카이브 연결**에서 저장 경로의 SFTP 목록을 확인한다. SSH 인증 테스트와 SFTP 접근·쓰기 권한 확인은 별개다.

설정 조회는 계정명과 공개키를 `***`로 반환하고 구성 여부를 별도 필드로 제공한다. SSH 테스트는 OpenSSH 명령을, 탐색과 업로드는 Paramiko를 사용한다. 두 경로 모두 앱 전용 개인키와 저장한 호스트 키를 사용하며 SSH agent와 비밀번호 인증을 사용하지 않는다. 저장한 호스트 키가 바뀌면 연결을 거절한다. 변경된 호스트 키를 화면에서 교체하는 기능은 없다.

| 컨테이너 경로 | 내용 |
| --- | --- |
| `/settings/address` | 원격 IP |
| `/settings/remote-root` | 원격 저장 절대경로 |
| `/settings/ssh/id_ed25519` | 앱 전용 개인키 |
| `/settings/ssh/id_ed25519.pub` | 공개키 |
| `/settings/ssh/public_key_copied` | 공개키 복사 완료 표시 |
| `/settings/known-photo-saver-<IP의 SHA-256>` | IP별 승인한 호스트 키 |
| `/settings/pending-host-key.json` | 승인 대기 호스트 키와 만료 토큰 |

Compose의 `settings` 볼륨은 API에 읽기·쓰기, 워커에 읽기 전용으로 마운트한다. 설정 파일 갱신에는 파일 잠금과 임시 파일 교체를 사용한다.

## 2. Source와 Destination

**Source**는 사용자가 이벤트 배치를 확정한 `managed` 파일과 연결된 XMP를 보여 주는 논리 트리다. 실제 원본은 `managed/<파일 ID>/<파일명>`에 있고, Source는 다음과 같이 구성한다.

```text
이벤트 폴더 / 장비 폴더 / 파일명
이벤트 폴더 / 소분류 폴더 / 장비 폴더 / 파일명
```

장비 폴더에는 사용자 지정 장비를 우선 적용하며, 장비를 명시적으로 미상으로 분류하면 `unknown`을 사용한다. 원본과 XMP는 각각 선택할 수 있고, 폴더를 선택하면 그 안의 원본과 XMP를 함께 선택한다.

**Destination**은 설정한 원격 루트 아래 실제 디렉터리를 조회한다. 폴더를 열 때마다 SFTP로 해당 경로의 목록을 읽으며 폴더를 먼저 정렬한다. 파일 크기·수정 시각도 반환한다. 심볼릭 링크는 링크로 표시하고 화면에서 하위 폴더로 열지 않는다. 앱의 `.photo-saver-*.part` 임시 파일을 포함한 숨김 항목도 목록에서 제외하지 않는다.

절대경로와 `..`를 포함한 상대경로를 거절하고, SFTP 정규화 결과가 원격 루트 밖이면 조회를 거절한다. 폴더 목록은 최대 10,000개이며 조회 중 15초가 지나면 시간 초과로 처리한다. 연결·인증 단계는 각각 5초, SFTP 채널은 10초 제한을 사용한다. 목록 응답은 캐시하지 않는다.

## 3. 업로드 목적지와 예약

Source에서 선택한 항목을 **업로드**하거나 Destination의 현재 영역 또는 폴더로 드래그하면 전송을 예약한다. 업로드는 현재 Source 위치를 기준으로 상대 구조를 유지한다.

| 선택 당시 Source 위치 | 선택 파일의 논리 경로 | Destination 위치 | 최종 상대경로 |
| --- | --- | --- | --- |
| 루트 | `260903_여행/GoPro/clip.MP4` | `backup` | `backup/260903_여행/GoPro/clip.MP4` |
| `260903_여행/GoPro` | `260903_여행/GoPro/clip.MP4` | `backup` | `backup/clip.MP4` |

예약 시 서버는 다음 조건을 확인한다.

- 파일이 카탈로그에서 `available`이고 이벤트 배치가 확정됐는지 확인한다.
- 선택한 원본 또는 XMP의 경로와 SHA-256이 있고 현재 Source 하위 항목인지 확인한다.
- 한 요청의 서로 다른 항목이 같은 목적지 경로를 사용하는지 검사한다. 충돌하면 전체 예약을 거절한다. 동일 항목의 중복 선택은 제거한다.
- Destination 조회 시 받은 연결 버전이 현재 설정과 같은지 확인한다. IP·계정·저장 루트·호스트 키·공개키 식별자로 연결 버전을 계산한다.

한 요청은 최대 10,000개 항목이다. 예약하면 목적지, 로컬 경로, SHA-256, 원본 fingerprint를 작업 payload에 고정한다. 설정 원문 대신 연결 버전 해시를 저장하며, 실행 전에 설정이 달라졌으면 실패한다. 이후 이벤트 이름이나 배치를 바꿔도 이미 예약한 목적지는 유지된다.

현재 작업 큐는 검사·이동·사진 삭제·XMP 연결·업로드를 통틀어 `queued` 또는 `running` 작업 하나만 허용한다. 업로드가 진행되는 동안 새 파일 작업을 예약할 수 없다.

## 4. SFTP 전송과 검증

워커는 예약한 항목을 순서대로 처리한다.

1. 원격 저장 루트를 정규화하고 필요한 하위 디렉터리를 만든다. 하위 경로에 일반 파일이나 심볼릭 링크가 있으면 실패한다.
2. 원본의 fingerprint를 확인하고 검증한 파일 디스크립터를 전송이 끝날 때까지 유지한다. XMP는 실행 시 fingerprint를 확보하고 예약된 SHA-256과 대조한다.
3. 목적지에 같은 이름의 일반 파일이 있으면 크기와 SHA-256을 확인한다. 원격 파일과 로컬 원본이 모두 예약된 해시와 같으면 `skipped`로 기록한다. 내용이 다르거나 일반 파일이 아니면 덮어쓰지 않고 실패한다.
4. 새 파일은 같은 디렉터리의 `.photo-saver-<작업 토큰>-<항목 번호>.part`에 배타적으로 생성한다. 같은 작업의 이전 임시 파일만 제거하고 처음부터 다시 쓴다.
5. 1 MiB 단위로 전송하면서 로컬 SHA-256과 크기를 검증하고 전송 후 fingerprint를 재확인한다.
6. 임시 파일 전체를 SFTP로 다시 읽어 SHA-256을 계산한다. 검증이 성공한 뒤 덮어쓰지 않는 SFTP `rename`으로 최종 이름을 게시하고 `uploaded`로 기록한다.

해시 검증은 원격 셸에서 실행하지 않고 SFTP 읽기로 수행한다. 업로드 후 전체 파일을 다시 내려 읽으므로 검증에도 네트워크 트래픽이 발생한다. 전송 중 목적지 파일이 새로 생기면 최종 이름 변경이 실패하며 기존 파일을 보존한다.

진행 결과는 현재 경로, 단계, 전체·완료 파일 수, 업로드·건너뜀·실패 수, 바이트 수를 포함한다. 진행 갱신은 최대 약 0.3초 간격으로 제한하며 파일별 경계에서는 즉시 저장한다. 건너뛴 파일도 처리한 바이트에 포함되므로 화면 수치는 실제 네트워크 송신량과 다를 수 있다. 오류 상세는 최대 100개를 보관한다.

## 5. 실패·취소·재시작

| 상태 | 동작 |
| --- | --- |
| `queued` | 아직 워커가 실행하지 않은 상태. 취소하면 즉시 `cancelled`로 바뀐다. |
| `running` | 실행 중. 취소 요청을 저장하면 워커가 다음 진행 저장 시 확인해 중단한다. |
| `done` | 모든 항목이 `uploaded` 또는 `skipped`로 처리됐다. |
| `failed` | 파일별 실패나 연결 오류가 발생했다. 파일별 실패 후에는 다음 파일 처리를 시도하며, 일부 성공도 그대로 남는다. |
| `cancelled` | 사용자가 중단했다. 이미 게시된 파일과 기록은 유지한다. |

전송 함수가 정상적으로 종료되거나 예외로 빠져나올 때는 해당 임시 파일 삭제를 시도한다. 프로세스 강제 종료나 통신 단절로 남은 임시 파일은 같은 작업을 재실행할 때 정리한다. 다른 작업의 임시 파일을 일괄 삭제하는 기능은 없다.

워커 재시작 시 `running` 작업을 `queued`로 돌리고 같은 payload를 다시 처리한다. 이미 최종 파일이 있으면 해시를 비교해 건너뛰고, 미완료 파일은 처음부터 보낸다. 바이트 위치부터 이어 보내지는 않는다. 최종 게시 직후 기록 전에 중단됐어도 재실행 시 동일 파일 검증으로 복구할 수 있다.

스토리지 전원이 꺼졌거나 연결에 실패한 작업은 `failed`가 된다. 자동 대기·백오프·재연결 예약은 없으므로 연결을 복구한 뒤 사용자가 다시 업로드해야 한다. 업로드는 로컬 원본이나 완료한 원격 파일을 삭제하지 않는다.

## 6. 파일 기록과 검증 이력

**파일 기록**은 SQLite 카탈로그를 조회하며 원격 스토리지에 연결하지 않는다.

- **보유 파일**: `managed` 원본, 연결된 XMP, 해시가 기록된 Incoming 검사 항목을 경로별로 표시한다. 파일명·현재/원래 경로·SHA-256·장비·이벤트·파일 ID로 검색하고 위치, XMP, 아카이브 검증 이력으로 필터링한다.
- **아카이브 기록**: 업로드 항목별 로컬 경로, SHA-256, 크기, 연결 식별자, 당시 원격 루트와 목적지, 결과, 검증·기록 시각, 오류를 표시한다. 이벤트·소분류·장비 트리와 페이지 이동을 제공한다. 기본 페이지 크기는 50개, API 상한은 100개다.

| 파일별 결과 | 의미 |
| --- | --- |
| `uploaded` | 새 파일을 업로드하고 해시를 검증했다. |
| `skipped` | 같은 목적지의 기존 파일과 로컬 파일이 예약된 해시와 일치했다. |
| `failed` | 해당 파일 처리에서 오류가 기록됐다. 검증 시각은 없다. |
| `legacy_verified` | 파일별 기록이 없는 과거 `done` 작업에서 복원한 완료 이력이다. 당시 원격 루트가 없을 수 있다. |
| `pending` | 파일별 기록이 없고 작업이 `queued` 또는 `running`이다. |
| `unknown` | 파일별 기록이 없는 실패·취소 작업 등의 항목이다. |

파일별 전송 결과는 `archive_entries`에 작업 ID와 항목 번호를 키로 저장한다. 작업 전체가 연결 단계에서 실패한 경우 모든 항목에 개별 `failed` 행을 만들지는 않으며, 기록 화면은 작업 payload를 보완 조회해 `unknown` 등으로 표시한다. 과거 형식의 전송도 같은 방식으로 표시한다.

검증 이력은 전송 당시의 사실이다. 현재 원격 파일의 존재·내용을 주기적으로 다시 확인하지 않는다. 보유 파일의 **아카이브 검증 기록 있음**은 파일 ID·원본/XMP 종류·현재 SHA-256이 검증 이력과 일치할 때만 표시한다. 기록 화면의 이벤트와 장비 분류는 현재 카탈로그를 따르고, 전송 당시 목적지 경로는 이력에 남는다.

## 7. 카탈로그 백업과 복원

**설정 → DB 백업 다운로드**는 SQLite Online Backup API로 일관된 `.sqlite3` 파일을 만든다. 파일명은 앱 기본 시간대 기준 `photo-saver-YYYYMMDD-HHMMSS.sqlite3`이며 응답 후 서버 임시 파일을 삭제한다. 백업과 복원 모두 전체 카탈로그 잠금을 사용하고, 현재 `queued` 또는 `running` 작업이 있으면 거절한다.

**백업 파일 선택 → 복원**은 최대 128 MiB의 SQLite 파일을 받아 현재 스키마의 데이터로 복사한다. 현재 카탈로그 데이터는 복원 내용으로 대체된다. 복원은 다음을 검사하고 한 트랜잭션으로 적용한다.

- SQLite `quick_check`, 필수 테이블과 컬럼, JSON 필드의 형식, 외래 키 관계를 검증한다.
- 이전 백업에서 빠질 수 있는 XMP·원래 경로 관련 컬럼과 `scan_xmp`, `archive_entries` 테이블을 허용한다.
- 백업 안의 `queued`·`running` 작업은 `failed`로 바꾼다. 이전 작업을 자동 재실행하지 않는다.
- 복원한 `media.moving`은 `missing`, `scan_files.deleting`은 `review`로 바꾼다. 복원 뒤 라이브러리를 새로 고쳐 실제 파일 상태를 확인한다.

백업 대상은 카탈로그 데이터다. 사진·영상·XMP 원본, 썸네일, `.env`, `/settings`의 IP·저장 경로·SSH 키·호스트 키는 포함하지 않는다. 복원은 해당 파일이나 원격 아카이브를 복구하지 않는다.

## 8. 현재 범위와 후속 설계

루트 README의 초기 설계 중 다음 항목은 현재 구현에 포함되지 않는다.

- rsync 전송, 원격 해시 보조 스크립트, 원격 파일 전체 인덱싱 및 변경 감지.
- 다른 원격 경로에서 동일 콘텐츠를 찾아 참조하거나 스토리지 내부에서 복사하는 기능.
- 충돌 파일에 해시 접미사를 붙이는 자동 이름 변경과 재승인 미리보기.
- OMV가 꺼진 동안 자동 대기하고 재시도하는 전송 스케줄러.
- 분석과 업로드의 병렬 실행.

현재 지원하는 중복 재사용은 **선택한 동일 목적지 경로의 파일**을 전송 시점에 검증해 건너뛰는 동작이다.
